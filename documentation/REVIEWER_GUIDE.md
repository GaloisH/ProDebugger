# ProDebugger: implementation and reproducible examples

ProDebugger is a platform for investigating recorded LLM agent failures. Its
**workbench** is the browser interface for browsing trajectories, inspecting
compiled evidence, following a diagnostic run and comparing candidate explanations.
ALFWorld and WebShop are the supplied domain profiles.

## Terminology and implementation boundaries

| Term | Meaning in this repository |
| --- | --- |
| Platform | ProDebugger as a whole: compiler, query interface, diagnostic workflow and workbench |
| Workbench | The browser interface served by `web/server.py` |
| DSL | The constrained interface over typed trajectory records, element operators and evidence provenance |
| Record SQL | The implemented SQL-style query surface of that interface; supports SELECT, CTEs, joins, filters and unions subject to validation |
| `TRACK_STATE` | Implemented operator for recorded state assignments of an entity and relation |
| `TRACE_STATE` | Not a callable operator in the current implementation; use `TRACK_STATE` in executable queries |
| Candidate / hypothesis | A proposed failure attribution to a recorded step and module |
| Selected diagnosis | The existing TRACE candidate selected by SUBMIT; selection does not establish causal truth |
| Reference annotation | The supplied benchmark label, kept outside the debugger's Parquet input fields |

The interface uses SQL syntax. Calling it a DSL describes its restricted record
access and evidence semantics; it does not imply a new general-purpose SQL engine.
See [the executable query implementation](../prodebugger/query_dsl.py),
[operator documentation](../prodebugger/prompts/query_dsl.md) and
[query checks](../checks/test_query_backend.py).

The implemented constraints include:

- Evidence retrieval uses targeted element functions such as `TRACK_ACTION`,
  `TRACK_STATE`, `SEARCH_TEXT` and `SOURCE`. Direct full-log tables (`steps`,
  `modules`, `facts`) and `RAW_STEP` are rejected. The operator documentation also
  describes allowed workflow metadata.
- Queries are read-only and validated. Literal operator arguments restrict how
  elements are requested; normal SQL combines the resulting evidence.
- Missing state, unresolved extraction and unavailable query branches remain
  unknown. A failed branch or an empty retrieval cannot establish that an event
  did not happen. Explicit filters and limits also restrict coverage.
- Fact results can retain `fid` and original source spans; source excerpts can
  retain `source_id`, step, module and offsets. Query column selection can omit
  these fields, so evidence interpretation must inspect the returned provenance.
- The TRACE workflow permits one query per investigator, including query errors.
  Candidates and citations are validated before SUBMIT compares them.
- Run logs preserve query text and returned evidence. Saved runs can be inspected
  and replayed; replay requires an actual saved transcript or finished run.
  Generated compilation records alone are not a recorded LLM diagnosis.

See [query recovery checks](../checks/test_query_recovery.py),
[manager checks](../checks/test_trace_manager.py) and
[forced-selection checks](../checks/test_forced_submit.py) for the corresponding
runtime behavior. Provenance edges support inspection, not proof of causation.

## Reproduce the two-environment examples

Install the [requirements](../requirements.txt) using the [setup instructions](../README.md#setup),
then run from the repository root in the activated environment:

```bash
python -B inspect_examples.py
```

This compiles the two included trajectories and executes one annotated read-only
query for each. It makes no network requests or model calls and needs no API key.

| Environment | Trajectory | Example action query |
| --- | --- | --- |
| ALFWorld | `GPT-4o_027_alfworld_task_027` | `TRACK_ACTION('go')` |
| WebShop | `GPT-4o_003_chat_b000_t00_e02-1e119842` | `TRACK_ACTION('search')` |

Inspect `artifacts/reviewer_examples/report.json` and each trajectory subdirectory:

- `record.json`: compiled task, entities, goals, Facts and rule evaluations;
- `steps.json`: original environment/agent steps and admissible actions;
- `query.sql`: the exact evidence query, with purpose and coverage comments;
- `query_result.json`: returned rows, Fact IDs, source spans and explicit limitations.

For example, the ALFWorld query is:

```sql
-- Purpose: inspect a few recorded actions with their Fact provenance.
-- LIMIT intentionally shows only the first five matches, not full coverage.
SELECT fid,step,rel,args,span,source_kind,parse_status
FROM TRACK_ACTION('go') ORDER BY step,fid LIMIT 5;
```

The [saved report](../EXAMPLE_REPORT.json) was generated by this script against the
published data. It shows two working compilation/query paths. It is not a
benchmark accuracy result or an online diagnosis. Neither reference failure
annotations nor suggested causal labels are used to construct these queries.

## Workbench and demonstration flow

```bash
python web/server.py
```

Open http://127.0.0.1:8770. The supplied Parquet catalog contains 66 ALFWorld and
39 WebShop trajectories. In Chat, search a trajectory ID and configure an online
run if a compatible provider and API key are available. Live diagnosis requires
that configuration; opening the workbench or running the offline script does not.

For an existing diagnostic run, the workbench lets a user:

1. Inspect the original trajectory and diagnostic phase activity.
2. Inspect recorded SQL queries, their evidence and linked source steps.
3. Explore compiled Facts, goals, entities and provenance in the DSL Graph.
4. Compare the selected hypothesis with other candidates and, when available,
   the benchmark reference annotation.

Replay reuses an existing run or transcript; this release does not bundle a
finished online run. The homepage's historical embedded case and screenshots may
refer to artifacts absent from a fresh clone. Treat them as interface illustrations,
not results generated by the offline examples. The current workbench does not
provide an arbitrary interactive SQL editor. To change the offline query, edit
`sql` in `inspect_examples.py` and rerun it; online investigators generate their
own queries under the workflow's one-query constraint.

## Interpreting results and extending to other traces

With available candidates, SUBMIT must select one even if TRACE reports
uncertainty. `diagnosed` indicates that a response passed the output protocol,
not that the selected cause is correct, unique or globally earliest. If TRACE
returns no candidates, the runner records `no_candidate` and skips SUBMIT.
Fields named `root` or `is_root_cause` remain in the existing output schema for
compatibility; interface labels describe them as a selected hypothesis or a
TRACE judgement.

The 105 released trajectories establish data availability. The two examples
establish offline executability across two environments. They do not establish
coverage of every failure pattern, diagnostic accuracy or transfer to a new
benchmark. Compilation can leave parsing gaps; rule violations are candidates
rather than confirmed mistakes.

For other traces, the current Parquet path expects `trajectory_id`, `task_type`
and `full_trajectory` with the supported message envelope. New environments need
a domain profile and parser validation; arbitrary user-entered tasks are not yet
implemented by the launcher. See [data fields](../core/data/README.md),
[domain profiles](../core/profiles) and [the input adapter](../core/data_io.py).
